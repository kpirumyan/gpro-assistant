# Синхронизация Истории Гонок: Финальный План

Это итоговый архитектурный план, согласованный в ходе нашего обсуждения.

## 1. Интерфейс пользователя (UI)
- **Режимы синхронизации (Toggle/Tabs)**:
  - *Режим 1: Одиночная гонка* (выбран по умолчанию). Поля по умолчанию заполняются последней сохраненной гонкой из БД. Пользователь указывает только `Сезон` и `Гонку`. Синхронизируется только она одна.
  - *Режим 2: Диапазон (Range)*. Пользователь вводит `Сезон От`, `Гонка От` и `Сезон До`, `Гонка До`.
- **Валидация**: Клиентская валидация отключает кнопку "Sync", если выбран обратный диапазон (`От > До`), и показывает пользователю понятное сообщение об ошибке (например, "Конечная гонка должна быть позже начальной").
- **Значения по умолчанию**: При загрузке страницы берем из нашей БД самую последнюю сохраненную гонку и подставляем ее во все поля. (Без запросов к GPRO API).
- **Процесс в 2 шага (Подготовка и Синхронизация)**:
  1. Пользователь нажимает кнопку **"Sync"**.
  2. Появляется окно подтверждения (или текст с кнопкой): *"Не хватает X гонок в базе. Будет потрачено X из 1000 ваших ежедневных API-запросов. Продолжить?"*.
  3. Пользователь подтверждает, и начинается загрузка с Прогресс-баром и кнопкой "Отмена".

## 2. Логика Подготовки (На Сервере)
Отвечая на ваш вопрос: **да, всю математику мы вынесем на сервер!**
Мы создадим Серверный Экшен `prepareSync(fromSeason, fromRace, toSeason, toRace)`:
1. Сервер генерирует полный список гонок в этом диапазоне.
2. Делает один `SELECT` в БД, чтобы найти уже существующие гонки.
3. Исключает существующие гонки из списка.
4. Возвращает клиенту итоговый массив недостающих гонок (например, 8 объектов `{season, race}`).
*Длина этого массива — это и есть тот самый X, который мы покажем пользователю перед стартом!*

## 3. Логика загрузки (Клиентский Батчинг)
1. После того как пользователь подтвердил загрузку X гонок, клиент (фронтенд) берет массив, который ему вернул сервер на этапе подготовки.
2. Клиент режет этот массив на "пачки" по 5 гонок.
3. Клиент в цикле отправляет каждую пачку на сервер через Серверный Экшен `syncRaceBatchAction`.
4. Сервер просто скачивает эти 5 гонок из GPRO API и кладет в БД.
5. Клиент обновляет Прогресс-бар.

## 4. Оптимизация и Безопасность
- Идеальное разделение ответственности: сервер считает и фильтрует данные, клиент управляет потоком (батчингом) и рисует UI, чтобы защитить сервер Vercel от тайм-аутов.
- Если GPRO API упал или гонки не существует (404 Not Found), сервер моментально возвращает ошибку, клиентский цикл прерывается, и мы показываем пользователю красное уведомление.
