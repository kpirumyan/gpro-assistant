# Загрузка и анализ данных о расходе топлива в прошедших гонках

Цель фичи: получать данные по прошедшим гонкам из GPRO API (эндпоинт `/RaceAnalysis`), сохранять сырой ответ, создавать снепшоты болида и пилота, а также рассчитывать минимальный и максимальный средний расход топлива на круг (и на дистанцию) с учетом неопределенности игровых данных.

## Ответы на вопросы и утвержденные архитектурные решения

1. **Ограничения API и параметры запроса:**
   Мы **обязательно** будем использовать параметр `SR` (Season, Race, например `SR=87,11`), чтобы запрашивать конкретную гонку. Делать запрос без параметров нельзя, так как API может упасть или тормозить из-за большой истории.
   
2. **Как запускать сбор данных (Рекомендация):**
   В интерфейсе настроек (или отдельной вкладке "Синхронизация") мы добавим кнопку **"Синхронизировать гонки"**. По клику будет вызываться Server Action. Он запросит текущий сезон/гонку (например, через эндпоинт `Calendar` или профиль) и начнет цикл (от последней прошедшей гонки назад). Скрипт будет запрашивать по одной гонке `SR=X,Y`. Если гонка уже есть в базе — цикл останавливается. Это самый надежный способ.

3. **Реляционная БД (Postgres) vs MongoDB:**
   PostgreSQL отлично справляется с JSON-данными благодаря типу `JSONB`. Он позволяет нам хранить "нереляционный" сырой ответ API со всеми плюсами NoSQL (индексация ключей внутри JSON, отсутствие жесткой схемы), сохраняя при этом возможность делать строгие связи (Foreign Keys) для аналитики. Переходить на MongoDB нет смысла — мы легко справимся с `JSONB`.

4. **Износ деталей в снепшотах:**
   Да, износ имеет смысл сохранить. В API уже есть поля `startWear` и `finishWear` для каждой детали. Мы добавим их в `race_car_snapshots`. Если они не понадобятся для расхода — мы их просто проигнорируем, но для будущей аналитики они уже будут лежать в структурированном виде.

5. **Быстрые круги и гранулярность сохранения:**
   Мы будем сохранять аналитику как **для каждого длинного стинта (>= 10 кругов) отдельно**, так и **для всей гонки в целом**. В таблице аналитики появятся колонки `type` (`'stint'` или `'full_race'`), `stintIndex` и `fastLapsCount` (подсчет кругов, где `boostLap` > 0).

6. **Финишное топливо и погрешность:**
   Для финишного остатка `finishFuel` мы **не применяем** правило `+3%`. Сколько осталось — столько и считаем точным значением. (Погрешность `X% ... X+3%` применяется только к пит-стопам `fuelLeft`).

7. **Расход на километраж (л/100км или км/л):**
   Помимо расхода на круг, мы заложим в таблицу колонки для расхода на километр. Если длина трассы нам известна (или будет известна позже из базы трасс), мы сможем вычислять расход в формате Л/100км. Пока мы будем собирать данные, расчеты можно вести в литрах на круг, а при визуализации переводить в дистанцию.

## Proposed Changes

### База данных (Drizzle ORM)
Создаем новые таблицы для хранения сырых данных и аналитики.

#### [NEW] `src/lib/db/schema.ts` (Дополнения)
- `race_analysis` (Сырые данные гонок)
  - `id` (PK)
  - `season` (integer)
  - `race` (integer)
  - `group` (text)
  - `rawData` (jsonb)
  - `createdAt`, `updatedAt`
  - *Unique constraint (season, race)*

- `race_fuel_analytics` (Вычисленные метрики топлива)
  - `id` (PK)
  - `raceAnalysisId` (FK -> `race_analysis.id`)
  - `type` (text) — `'stint'` или `'full_race'`
  - `stintIndex` (integer, nullable) — номер стинта (1, 2, 3...)
  - `lapsAnalyzed` (integer) — количество кругов в отрезке
  - `fastLapsCount` (integer) — количество быстрых кругов (`boostLap` > 0)
  - `avgFuelPerLapMin` (numeric)
  - `avgFuelPerLapMax` (numeric)
  - `createdAt`, `updatedAt`

- `race_car_snapshots` (Состояние машины на момент гонки)
  - `id` (PK)
  - `raceAnalysisId` (FK)
  - `power`, `handling`, `acceleration` (integer)
  - Для каждой детали (Chassis, Engine, FWing и т.д.): `lvl` (integer), `startWear` (integer), `finishWear` (integer)

- `race_driver_snapshots` (Состояние пилота на момент гонки)
  - `id` (PK)
  - `raceAnalysisId` (FK)
  - `name` (text)
  - `overall`, `concentration`, `talent`, `aggression`, `experience`, `technicalInsight`, `stamina`, `charisma`, `motivation`, `reputation`, `weight` (integer)

### Бизнес-логика (Сервисный слой)

#### [NEW] `src/lib/services/race-analysis.service.ts`
Создание сервиса со следующим функционалом:

1. **Синхронизация:** 
   - Начиная с последней известной гонки менеджера (можно получить из профиля или календаря), делаем запросы `fetchRaceAnalysis` в цикле с убыванием (e.g. S99 R8 -> S99 R7).
   - Сохраняем в `race_analysis`.
   - Если получаем ошибку 404/Недоступно или находим гонку, которая уже есть в базе, — прерываем цикл.

2. **Парсинг Снепшотов:**
   - Извлечение данных объекта `driver` в таблицу `race_driver_snapshots`.
   - Извлечение данных `carPower`, `chassis`, `engine` и т.д. (включая `startWear` и `finishWear`) в таблицу `race_car_snapshots`.

3. **Алгоритм расчета расхода топлива:**
   - Читаем массив `pits` и `laps` (для подсчета `boostLap`).
   - Итерируемся по стинтам:
     - **Стинт 1:** старт = `startFuel`, финиш = `pits[0].fuelLeft` (погрешность от `X%` до `X+3%`).
     - **Стинт N (промежуточный):** старт = `pits[N-1].refilledTo` (точное значение), финиш = `pits[N].fuelLeft` (погрешность от `X%` до `X+3%`).
     - **Последний Стинт (до финиша):** старт = `pits[last].refilledTo`, финиш = `finishFuel` (точное значение, **без добавления 3%**).
   - Вычисляем количество кругов и быстрых кругов (`boostLap`) для каждого стинта.
   - Если стинт >= 10 кругов:
     - Рассчитываем `stintConsumedMin` и `stintConsumedMax`.
     - Делим на количество кругов, получаем `avgFuelPerLapMin` и `Max`.
     - Создаем запись в `race_fuel_analytics` с `type='stint'` и `stintIndex`.
   - **Полная гонка:**
     - Суммируем `stintConsumedMin` и `Max` по всем валидным стинтам (или по всем стинтам гонки, если они все подходят).
     - Суммируем круги.
     - Создаем запись `type='full_race'`.
